# Internals

[Coywolf Pack documentation](README.md) · [Getting started](../README.md#getting-started)

## Database reads

A page that isn't in the edge cache yet is built by the Worker, and every D1 round trip costs it about 25–30 ms. The pack keeps its share to about one:

- **Settings with the switches.** The feature switches, the settings page renders need (schema, videos player, discovery, code theme, review style…), the deployed version and the settings generation are one query, cached per Worker isolate for five minutes. A save through the pack's admin pages applies at once in the isolate that made it.
- **Settings generation.** Every successful pack admin save writes a new generation (`plugin:coywolf-pack:state:settingsGeneration`). A successful POST to a pack route counts as a save unless the route is public or declared read-only where it's defined (`readOnlyRoute` in `src/core/routes.ts`: previews, pickers' lists, connection tests, the video library listing…); those clear nothing, record no generation and don't restart cache warming, and `src/pageCache/lib.test.mjs` lists them. Other isolates see it on their next read of the switches (within five minutes) and drop everything they derived from settings (schema config, player settings, redirect patterns…), which otherwise lasts up to ten minutes. Because those isolates may render pages with the old settings in the meantime, a save that clears the page cache clears again about five minutes later (see [Page cache](performance.md#page-cache)). Pages in the edge cache are tagged with the generation they were rendered with (`coywolf-gen-<id>`; `coywolf-gen-0` before a site's first save, `coywolf-gen-unknown` when an isolate couldn't tell), and the generation row keeps the generations replaced in the last five minutes (`recent`), so after a save that cleared every page that second clear is by those tags only (`src/core/generation.ts`). More than 40 of them (dozens of saves in five minutes) clear everything instead: Cloudflare takes at most 100 tags and path prefixes per purge. This is only as correct as the per-isolate caches: anything a page renders from settings or from data the pack's admin routes change (schema config, player settings, redirect rules, file records, the video embed index…) must be kept with the settings epoch (`isCurrent()` in `src/core/features.ts`), so an isolate that has read a new generation never renders with the old data under the new generation's tag. A cache with only a lifetime would keep such a page for days. Changes made outside the pack's admin pages (a byline's profile in EmDash) show up within ten minutes.
- **One query per entry.** An entry's Schema override, Videos embed index and AI entities are one query (and its blocks, for review schema, when the theme didn't pass the entry), read once per request however many hooks ask.
- **Redirects from memory.** A request whose path is no exact redirect source makes no redirect read at all: each isolate keeps the rules' index (patterns and the set of exact sources) in memory (see [Redirect Manager](redirects.md)).
- **Batched.** The pack reads D1 through the raw binding (`env.DB`), which EmDash's per-request session (and its `coalesce` option) never sees, so reads the pack starts in the same moment are sent as one `db.batch()`: one round trip. A request's redirect lookup goes in the same batch as the feature switches when those aren't cached; on a page, the entry's data, image dimensions and video details are another.
- **From the theme.** Pass the entry you rendered as `coywolf.entry` on the page context (see [Schema & Social](schema.md#pass-the-entry-to-save-reads)) and the pack doesn't read its bylines or blocks again.

## Shared reads have deadlines

The pack shares work that's under way between the requests of a Worker isolate: the feature switches' read, the redirect rules' index, the robots.txt takeover, a cold llms.txt build. On Workers, a request's I/O and timers belong to that request, and a request that's canceled (Cloudflare ends it at 100 seconds, its client leaves, a background task is cut off at 30 seconds) never settles what it started. Before 0.35.16 a later request waited for that forever, and so did every request after it, until the isolate was replaced: pages answered 524 after 100 seconds with 1–10 ms of CPU (coywolf.com, November 7 and 9, 2026). Now (`src/core/single-flight.ts`):

- **Anchored.** A shared read is handed to `waitUntil` as it starts, so a request that answers before the read is done (a request answered early, a client that leaves) still finishes it for the others.
- **Bounded.** A request that finds a read under way checks for its result on its own timers, never waiting on the other request's promise, and at most 2.5 seconds after that read started (10 s for a cold llms.txt or news sitemap build). Then it reads for itself, and its read replaces the stale one; other requests that gave up in the same moment wait for that fresh read (the same way, and at most once more) instead of each reading again. The log says `coywolf-pack: shared read stalled: … didn't settle within 2500 ms; reading again`. With D1 healthy, that costs the request the 2.5 s wait plus a normal read (tens of milliseconds).
- **Failing closed.** Every pack D1 read has a 5-second deadline; a read that times out counts as a failed read (features at their defaults, the page kept out of the edge cache), never a hang. So when D1 itself stops answering, a request fails after about 7.5 seconds at worst (2.5 s waiting for another's read, then its own 5 s read; one that waited on two reads in a row, 10 s), not the 100 s wall. The pack also batches same-tick reads per request (`src/core/d1-batch.ts`); a batch whose flush timer was dropped is taken over by a later read of the same request, but what protects every request is the per-read deadline.
- **Background work too.** Cache warming visits and steps, crops made on first use, video poster copies, download counts, and Discovery's Crawler Hints reads all have deadlines, so one stuck job can't stop the ones after it.

All the deadlines, with why each is what it is, are in `DEADLINES` in `src/core/single-flight.ts`.

## Which Cloudflare token a feature uses

Every Cloudflare feature reads its token through `cloudflareToken()` (`src/core/cloudflare-token.ts`), in this order:

1. a token typed on the page for one action (Set up media host, a Checkup fix, a Retention check), used once unless the page saves it;
2. the **Cloudflare API token** saved on the plugin's Settings page (`cloudflareApiToken`);
3. the feature's older saved token: `usageApiToken` (Cloudflare usage, Insights, Crawler Hints, the checkup's reading), `cloudflareSetupToken` (Checkup fixes), `imagesApiToken`, `videosApiToken`, `backupsCloudflareToken`, `socialImagesApiToken`, `robotsRadarToken`;
4. the feature's older Worker secret: `USAGE_API_TOKEN`, `IMAGES_API_TOKEN`, `CF_STREAM_TOKEN`, `BROWSER_RUN_API_TOKEN`, `RADAR_API_TOKEN`, or for Retention on Cloudflare the restore token's secret (`BACKUPS_API_TOKEN`, or `backups.restore.tokenSecret`);
5. the `CLOUDFLARE_API_TOKEN` Worker secret, last, so a site that holds it for another reason keeps using its older tokens.

So a site without the `CLOUDFLARE_API_TOKEN` Worker secret works exactly as before until the new token is saved, and then the new token wins everywhere. A site that has that secret (for wrangler, or an earlier Clean Image URLs or Backups setup, which already read it) finds it now also serves every feature that has no older token of its own: Cloudflare usage, Insights, Crawler Hints, Cloudflare Checkup (reading and fixes), Videos, Social Images, the Radar sync and large uploads. Where that secret lacks a permission, those pages show a permission error instead of a setup step, and the weekly Radar sync records a failure. Which token is used never depends on Cloudflare's answer: a refused call isn't retried with another token, and its error names the token that was used (`tokenName()`: the Cloudflare API token, or the older token or Worker secret). A saved token that can't be decrypted is skipped, and reported when nothing else is found. Restores never read this order: they use only the restore token, so D1 → Edit stays out of the token saved in the database. Large uploads read only steps 2 and 5, and a complete saved R2 key pair wins over both.

Module pages hide their own token fields only for the token saved on Settings. With only the `CLOUDFLARE_API_TOKEN` Worker secret, they say so and keep their own token field under **Advanced**, since a token saved there outranks the Worker secret.

**Features → Cloudflare API token → Remove older tokens** (`cloudflare-token/clear-older`) works only with the token saved on Settings, never with the Worker secret alone, and only after Cloudflare says that token is active (its verify endpoint) and sees exactly one account (`GET /accounts`). Otherwise it removes nothing and says why.

The account is `cloudflareAccountId()`: the page's own account ID, `CF_ACCOUNT_ID` or `CLOUDFLARE_ACCOUNT_ID`, Clean Image URLs' account ID, the account of a zone the token found (Insights), the account found before for this token, else `GET /accounts` when it lists exactly one. That answer is kept in plugin KV (`state:cloudflare:account`, the last four tokens' accounts) by a fingerprint of the token (16 hex digits of a prefixed SHA-256, never part of the token's own hash), so another token looks again. Only an answer counts: a token Cloudflare says sees no account or several isn't asked again for five minutes per isolate, while an error status, a network error or a timeout (8 seconds) is asked again next time. Cloudflare usage keeps using the Worker and database it found for the deployed version while the lookup fails. R2's S3 keys (`r2S3Credentials()`) are the token's ID, from `/accounts/{id}/tokens/verify` for an account token (`cfat_…`) or `/user/tokens/verify` for any other (then the other one, since older account tokens have no prefix), kept in KV by fingerprint (`state:cloudflare:tokenId`, the last four tokens), and the token's SHA-256 in hex, worked out on each call and never stored.

Bucket names come from the site's own Worker (`src/core/worker-bindings.ts`): `findWorkerScript()` finds the account's script whose current deployment runs this isolate's version (`CF_VERSION_METADATA`; `GET /accounts/{id}/workers/scripts`, most recently changed first, then each one's `/deployments`), and `workerBindings()` reads `result.bindings` of [`GET /accounts/{id}/workers/scripts/{name}/settings`](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/script_and_version_settings/methods/get/), where an R2 binding is `{ type: "r2_bucket", name, bucket_name, jurisdiction? }`. Cloudflare usage finds its D1 database with the same two calls. `boundBucket()` (large uploads, Set up media host, Retention on Cloudflare) uses the token and account the feature already resolved, with an 8-second deadline per call, and keeps every R2 binding it read in plugin KV (`state:cloudflare:buckets`, the last four Worker versions) by Worker version, account and token fingerprint; a new version starts with the Worker found before. Only answers count. A Worker that wasn't found (every script's deployments answered, a 404 meaning no match) and a refusal (401/403: the token lacks Workers → Metadata Read-Only) aren't asked about again for five minutes per isolate. A failed deployments read with no match, settings without a `bindings` list, a Workers list that isn't a list, or a lookup past its total budget (`DEADLINES.workerLookupMs`, 15 seconds) is no answer: nothing is remembered, and the next look asks again. Cloudflare usage keeps its earlier behavior (a failed deployments read counts as not found there). A bucket name saved on the page always wins and skips the lookup in the upload, setup and retention paths; the pages still show what was found. Nothing on a public page render looks a bucket up.

The Settings page shows the four fields people fill in; `src/core/settings-enhance.ts` hides the older ones while they're empty, puts the saved ones behind **Older tokens (N)**, and hides `videosWebhookSecret`. All of them stay declared in `src/core/secrets.ts`, since reading an encrypted value whose key isn't declared throws.

## EmDash internals the pack relies on

Some features depend on EmDash behavior that EmDash doesn't promise to plugins. If EmDash changes it, the feature stops working without an error: no trash prompt, no guides, a query that reads nothing. `test/emdash-contract.test.mjs` checks each item below against the installed EmDash, using its real migrations, its plugin context, its admin bundle and Kumo's markup. CI runs it for the EmDash version the sites run and for the latest release (see [Releasing](releasing.md#ci)), so an EmDash change fails CI before the sites upgrade. Use this list when reviewing an EmDash upgrade.

**Checked by the contract test:**

- **Raw SQL.** Every SQL string in `src` that names EmDash's tables (`options`, `_plugin_storage`, `media`, `ec_*`, `_emdash_collections`, `_emdash_fields`, `_emdash_seo`, `_emdash_fts_*`, `taxonomies`, `content_taxonomies`) is prepared against a database built by EmDash's own migrations. That covers every table, column and `ON CONFLICT` target, and every `INSERT` names the columns EmDash requires. The test reads the SQL from the source files. A template value it doesn't know (added to `EXPRESSIONS` in the test), or a line naming those tables that it couldn't read, fails it. The backup dump and restore are left out because they copy whatever tables exist.
- **Media host from EmDash's storage.** EmDash's build-time config module (`virtual:emdash/config`) is its serializable config as JSON, with `storage` as the site configured it, so the pack reads `storage.config.publicUrl` there (`src/images/settings.ts`). A storage adapter's public URL for a key is `publicUrl` with trailing slashes removed, then `/<key>` (EmDash's S3 adapter is checked; `@emdash-cms/cloudflare`'s `r2()` isn't a pack dependency, so its identical `getPublicUrl` is checked by hand at an upgrade), and without a storage adapter it's `/_emdash/api/media/file/<key>`. The pack recognizes both forms as media-library files.
- **Search.** EmDash's FTS tables are `id`, `locale`, then the searchable fields (the pack's `bm25` weights and `snippet` column count on it). `search_config` is the JSON `parseSearchConfig` reads, and live search finds a published entry through EmDash's FTS triggers.
- **Option rows.** `ctx.kv` keys are `plugin:coywolf-pack:<key>` rows of `options`, `ctx.settings` keys are `plugin:coywolf-pack:settings:<key>`, and values are JSON. The pack's raw reads (the feature switches, registered settings) see what EmDash writes, and EmDash reads what the pack writes raw (the settings generation). Rows the pack writes into `_plugin_storage` (stored image sizes) are documents `ctx.storage` reads.
- **Plugin APIs.** `ctx.kv.list(prefix)` returns keys without the plugin prefix and takes `_` and `%` literally. `compareAndSet(key, null, …)` creates only when absent, a revision replaces only that revision, and the result is `{ applied, revision }`. The same holds for `ctx.kv`, `ctx.settings` and storage collections, and for `compareAndDelete`. Storage `updateIf` applies counter deltas, and `ctx.cron` schedules, lists and cancels by name. `ctx.redirects` (capability `redirects:write`) lists EmDash's slug-change redirects by `auto` and group (`Auto: slug change`, the group EmDash's content update writes them under), `get` returns the revision `delete` takes, and a stale revision is refused: Slug changes delete EmDash's row for the same change that way (`dropEmDashAuto` in `src/redirects/slug-changes.ts`), so EmDash's write lock, loop cache and published redirects see the delete.
- **Email and users (Alerts & Digest).** With `email:send`, `ctx.email` is undefined until an email provider is selected (Settings → Email), which is how the Alerts page knows to show its setup steps; once one is, `ctx.email.send({ to, subject, text, html })` reaches the provider's `email:deliver` hook with the pack's id as the source. With `users:read`, `ctx.users.list({ role: 50 })` lists the admins (the default recipients) with their email addresses.
- **Secret settings.** A key declared `type: "secret"` is stored encrypted, so the pack never reads one with raw SQL. Reading an encrypted value whose key isn't declared throws, including from `list(prefix)`. No secret, current or retired, starts with `schema`, the only prefix the pack lists. EmDash's Settings page API returns the labels as declared and reports secrets as set without returning them, and what it saves is what `ctx.settings` reads.
- **Sidebar.** `definePlugin` keeps `admin.pages` and `admin.widgets` as getters, and EmDash builds the admin manifest from them on each request, so a module switched off leaves the sidebar without a deploy.
- **`page:metadata`.** EmDash accepts the kinds the pack contributes (`jsonld`, `meta`, `property`). Plugin contributions come before core's, and the first one wins. Core's JSON-LD is `id: "primary"`, so the pack's graph replaces it. The page context the hooks get keeps a theme's extra keys (`coywolf.entry`, `coywolf.videos`…).
- **Routes.** EmDash's routes that the pack calls, links to or watches exist, with the methods it uses: `POST /_emdash/api/settings`, `GET /_emdash/api/manifest`, the content routes, the media routes (including `PUT …/replace`), plugin routes, search, and the admin.
- **Trash prompt.** EmDash's admin sends its content calls through the global `fetch`, looked up at call time, so the pack's `window.fetch` wrapper sees them. A move to trash is `DELETE /_emdash/api/content/<collection>/<id>`, an unpublish is `POST …/unpublish`, and both may have a `?locale=` query.
- **Sidebar refresh.** The admin's manifest query key is `["manifest"]`. The admin layout shows its loading screen only before the first manifest, so a refetch keeps a plugin page mounted and scrolled (it scrolls inside the shell's `<main>`). The admin brings its own React Query, so a site can have two copies and the pack's `useQueryClient()` may not see the admin's client: the Features page refreshes the manifest through the client on the router's context (`refreshAdminManifest` in `src/admin/extensions.ts`).
- **Settings saves.** The body of `POST /_emdash/api/settings` has `seo` at its top level. Once EmDash has a staging setting (1.5), the test fails if staging isn't saved there too.
- **Settings page guides.** The page is `/_emdash/admin/plugins-manager/<id>/settings`, its form is `#plugin-settings-form`, and each secret is Kumo's `Input` with the schema's label and description. Rendered with the installed Kumo, that input points to its label and description with `aria-labelledby` and `aria-describedby`. The pack's script then finds every guided field by its label and adds the guides.
- **Settings page older tokens.** The fields are siblings in one container, and each secret is a `div` holding Kumo's `Input`, then a `type="button"` **Clear stored value** button rendered only while a value is saved and not cleared. The script reads that button as "saved" (in any admin language), hides each field's `div` in place and adds its own toggle beside them; rendered as EmDash does, React's nodes stay where they were.
- **Cookies.** Astro keeps a request's cookies on the response under `Symbol.for("astro.cookies")`, and they survive the pack's admin page rewrite.
- **Admin router.** EmDash's admin is a TanStack Router app with basepath `/_emdash/admin`, and TanStack's Router puts itself on `window.__TSR_ROUTER__`. The pack's admin pages use it (`src/admin/router.ts`) for in-admin links that don't reload the app and for the unsaved-changes guard, which blocks through `router.history.block` as EmDash's own `UnsavedChangesGuard` does with `useBlocker`. Without it, links load the page and the guard falls back to the browser's prompt on reload or close.
- **Plugin pages.** EmDash renders a plugin page bare (no error boundary or `Suspense`) inside its `<Toasty>` and `RouterProvider`, so the pack's `packPage()` adds the boundary and `Suspense` for its lazy-loaded pages, and its save results use EmDash's toast stack.
- **Entry editor panels and list columns.** EmDash's admin imports the plugin's admin entry as a namespace, so its `contentEditorPanels` and `contentListColumns` exports reach it. It picks them with a synchronous `collections(collection)` predicate and `minRole`, re-run when `manifest.plugins` changes, renders a panel with `{ collection, entry, locale }` and a cell with `{ collection, item, locale, visibleItems }`. Its `createAdminRouter` puts the React Query client on the router's context, where the manifest is under `["manifest"]`, and the manifest's plugin entry lists `plugin.admin.pages`. The pack's predicate (`packPageOn` in `src/admin/extensions.ts`) reads that manifest, so a panel shows exactly while its module's page is in the sidebar; when it can't be read, nothing shows.
- **First install.** EmDash runs `plugin:install`, then `plugin:activate`, once for a config plugin with no `_plugin_state` row. That's how the pack tells a new site from one set up before 0.36.0 (the 0.36.0 defaults, below).
- **Versions.** The installed Kumo is the version EmDash's admin pins. EmDash's admin uses React, React Query and Phosphor majors that are in the pack's peer ranges, so they share one copy.

**Not checked (review by hand at an EmDash upgrade):**

- D1 itself. SQLite stands in for it, so D1's own limits (statement size, bound parameters, batch behavior) aren't covered.
- Astro's route cache object (`context.cache`). The middleware wraps its `invalidate` to notice content writes (`watchInvalidation` in `src/pageCache/lib.ts`), which assumes EmDash calls `cache.invalidate(…)` on the object it's handed.
- How EmDash's admin behaves in a browser beyond the Settings page markup above, such as single-page navigation to the Settings page and when the guides script's `MutationObserver` runs.
- Raw writes and revisions. The pack's raw upserts of `options` rows don't change their `revision`, so a key the pack writes raw must not also be compare-and-set through `ctx.kv` or `ctx.settings`. Today none is (the settings generation, cache warming state, page cache version, image sizes state and video posters are only written raw). The robots.txt config's first write is a raw insert with a new revision, and later writes go through `ctx.settings`.
- Class names in EmDash's precompiled admin stylesheet: `test/admin-classes.test.mjs` checks those.

## The 0.36.0 feature defaults

Redirect Manager, its Slug changes part and Backups were on by default until 0.36.0; they now start off. Their `FeatureDef`s have `default: false` and `legacyDefault: true` (`src/redirects/pack.ts`, `src/backups/pack.ts`). The stored switches (`plugin:coywolf-pack:settings:features`) carry a `_defaults036: true` marker once a site's defaults are recorded; until then, `resolveFeatures` uses `legacyDefault`, so an existing site, and any read that comes first or fails (the middleware's fallback resolves from nothing), keeps them on.

`recordDefaults` (`src/core/features.ts`) records them once, by compare-and-set on the switches:

- In `plugin:install`, which EmDash runs only when it first records the plugin on a site: if the pack has nothing stored (no switches, no setting or KV row other than its housekeeping rows, no storage document), it's a new site, so only the marker is stored and the new defaults apply. Install first leaves a flag (`state:freshInstall`, and one in the isolate), so if its recording fails, a later call still records the site as new while it has no pack data; the flag goes once the defaults are recorded. The housekeeping rows, which the pack writes on any site by itself, are the flag, `pageCache:version`, `pageCache:warmState` and `state:discovery:indexnowRetired`.
- Everywhere else (`plugin:activate`, the Features page's list, a save of the switches), and on any doubt (stored switches, any pack data, a read that fails): it's an existing site, so `legacyDefault` is stored for each of those features the site hadn't chosen, then the marker.

A new feature that starts off needs none of this. Use `legacyDefault` only when changing a default an existing feature already had.

## Scheduled tasks

EmDash runs every scheduled task that's due in one invocation (`plugins/cron.ts`, up to 10 a tick), and the sites' Cron Trigger fires hourly at minute 0, so on Workers Free all the due tasks share one 50-query D1 budget. Each task's handler first reads the feature switches and returns when its feature is off. A task marked `onlyWhileOn` (`TaskDef` in `src/core/module.ts`) goes further: it's scheduled only while its feature is on. The Features page's list and save, and `plugin:activate`, schedule or cancel it to match the switches (`ensureTasks` in `src/core/compose.ts`), and if it fires while its feature is off it cancels itself. Content Audit, Alerts & Digest and Social Images use it, and their weekly tasks run at quiet hours (Wednesday 04:00 and Monday 13:00 UTC), not at Sunday midnight when `@weekly`, `@daily` and `@hourly` tasks all fall due. Their steps size themselves for Workers Free (20 D1 statements for an audit step, 4 images an hour) unless the Cloudflare usage card has seen the Paid plan (`src/core/plan.ts`).
