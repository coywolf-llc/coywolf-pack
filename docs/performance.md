# Performance

[Coywolf Pack documentation](README.md) · [Getting started](../README.md#getting-started)

## Faster sites

EmDash on Cloudflare builds every page in a Worker, and a Worker that hasn't run recently in a data center has to start up, load EmDash and query D1 before it can answer. On coywolf.com that meant 1.1–2 seconds before the first byte and a mobile PageSpeed Speed Index of 5–8 seconds. With Coywolf Pack's performance features, the same site scores 100 in every PageSpeed category.

| What it improves | How |
| --- | --- |
| **First visits** | Keeps Cloudflare's Workers Cache (the edge HTML cache in front of the Worker) correct, so pages can stay cached for days: it clears the pages pack settings change, and sets page lifetimes at runtime. Each deploy starts with an empty cache. Cached pages answer in 60–90 ms instead of 1–2 s. |
| **Clearing the cache** | **Plugins → Performance → Clear pages and images**. Cloudflare's zone "Purge Everything" doesn't reach Workers Cache, which belongs to the Worker. Settings that don't change pages (backups, the link report) don't clear it, redirect edits clear only cached redirects, and robots.txt rules clear only `/robots.txt`. |
| **Cold pages after a clear** | Optional cache warming: after a deploy, a full clear or (a minute later) content edits, every page in the sitemap, plus the section pages the home page links to (category archives sitemaps often leave out), is visited in the background of the site's own traffic (home page and its menu pages first, then newest posts), so visitors and crawlers get cached pages instead of waiting for them to be built. |
| **Images** | Serves media from a `media.` subdomain (R2 custom domain + Image Transformations), never through the Worker, with clean resized URLs, a one-year Cache Rule, responsive `srcset` helpers, and width/height lookups for images that have none (WordPress imports), so layouts don't shift. |
| **Live search** | Results as you type in tens of milliseconds: an instant title index in the browser, an edge cache keyed to content changes, and 2–3 D1 queries instead of 25–31. |
| **Redirects** | Answered by middleware from rules cached per isolate, before EmDash renders anything, then kept in the edge cache (tagged `coywolf-redirects`) until a redirect edit clears them. |
| **Fewer D1 round trips** | Pages that aren't cached yet cost the pack about one D1 round trip: settings come with the feature switches' query (cached per isolate for five minutes), an entry's pack data is one query, and the pack's own reads of a moment go to D1 as one batch. See [Database reads](internals.md). |
| **No client JavaScript where it isn't needed** | Code highlighting, tables of contents, breadcrumbs, reviews and schema are rendered on the server. |

See [Page cache](#page-cache) for setup.

## Page cache

For sites that put Cloudflare's [Workers Cache](https://developers.cloudflare.com/workers/cache/) in front of the Worker, which serves cached pages without running the Worker. That's what makes first visits fast: a cold Worker spends a second or more starting up and querying D1. Turn it on in the site, as in EmDash's Cloudflare guide:

```js
// astro.config.mjs
import { cacheCloudflare } from "@astrojs/cloudflare/cache";
export default defineConfig({
	cache: { provider: cacheCloudflare() },
	routeRules: { "/": { maxAge: 3600, swr: 86400 }, "/[...path]": { maxAge: 3600, swr: 86400 } },
});
```

and add `"version_metadata": { "binding": "CF_VERSION_METADATA" }` to `wrangler.jsonc`.

EmDash clears the pages it tagged when content, menus or site settings change. **Plugins → Performance** (always on, right below Coywolf Pack; on a site without Workers Cache it does nothing) covers the rest:

- **After a deploy**: Workers Cache keeps each Worker version's pages apart (the version is part of the cache key; see Cloudflare's [cache keys](https://developers.cloudflare.com/workers/cache/cache-keys/)), so a deploy starts from an empty cache by itself and theme and code changes show up right away. The pack doesn't spend a purge on it (purges share a small account-wide budget: 5 a minute, with EmDash's content purges): the first request a new version handles only records the version, once (a conditional write, so racing isolates agree), and starts cache warming when it's on.
  - **Sites that share the cache across deploys** (`"cache": { "enabled": true, "cross_version_cache": true }` in `wrangler.jsonc`) keep serving the previous deploy's pages, so they need the old behavior: set the pack's `pageCache` option and the first request of a new version clears every cached page before recording it (a refused purge isn't recorded, so the next isolate tries again):

    ```js
    // astro.config.mjs (coywolf.com)
    coywolfPlugin({ pageCache: { crossVersionCache: true } })
    ```

    Without `cross_version_cache` leave it off: the purge would clear nothing anyone can reach.
- **After Coywolf Pack settings change**: a successful admin save that changes page output (schema, blocks, videos, images, feature switches…) clears every cached page (see Scoped clearing below). Routes anyone can call (search, discovery files, the video player's actions) and the signed Stream webhook aren't admin saves and never clear everything: the webhook clears only the pages that embed its video (see [Videos](videos.md)). Nor are the admin pages' reads (a schema preview, an entry or media picker, a connection test, the video library listing…): they're declared read-only where they're defined and clear nothing (see [Internals](internals.md#database-reads)). Other Worker isolates may keep the old settings for up to five minutes (see [Database reads](internals.md)), so pages they render meanwhile could be cached with them: about five minutes after the save, the first request in any isolate clears those pages (a "settling" clear). Every response the pack lets into the edge cache carries a tag naming the settings generation its isolate rendered it with (`coywolf-gen-<id>`, read with the switches, so it always matches the settings used), so after a save that cleared every page the settling clear removes only the generations isolates could still have had (usually none or a handful of pages), not every page again, and it doesn't restart the warm-up. Saves that clear less (redirects, robots.txt) settle the same scope again; a redirect save's settle includes the pages at its new sources, which an isolate that hadn't seen the new rule yet may have rendered instead of redirecting.
- **Page cache lifetimes**: how many days the edge keeps a page (default 7) and how many more days it may serve it while fetching a fresh copy in the background (default 1). They replace the `routeRules` lifetimes on the routes the site made cacheable, at runtime, so no deploy is needed. Routes without a route rule are never cached by this.
- **Not-found pages** (off until an admin turns on **Keep "not found" pages for 5 minutes**): EmDash and the sites' middleware keep 404s out of the edge cache, so every probe and dead link renders the site's 404 page (with its D1 queries). With this on, a GET answered 404 on a route the site made cacheable is kept at the edge for 5 minutes (no stale serving), tagged `coywolf-404`, replacing that choice; no other status changes. Every content change EmDash clears (a save, publish, unpublish or delete through the admin, its API or MCP) clears them too, in the same purge call, so a page published at an address someone just probed shows up at once; a scheduled publish (no request) shows within the 5 minutes. Never for EmDash's own URLs (`/_emdash/…`), a response marked `private` or `no-store`, one that sets a cookie, anything rendered for a signed-in user (EmDash keeps those out), or a 404 rendered after one of the pack's reads failed. Setting `pageCacheNotFound`, read with the switches. Turning it on or off clears nothing.
- **After going live**: EmDash's staging mode (EmDash 1.5+) puts `noindex, nofollow` on every page until the site goes live. Going live, or switching back to staging, under **Settings → General → Site Status** clears every cached page (and restarts warming), so search engines don't get cached pages with the old robots tag.
- **Media cache**: shows whether the media host (Clean Image URLs) has a Cloudflare Cache Rule, and **Cache media for a year** adds one (edge and browser TTL one year; media file names never change). Needs the Clean Image URLs token with **Zone → Cache Rules → Edit**. Other cache rules on the zone are kept.
- **Cache warming** (off until an admin turns it on): after a deploy or a full clear, the pack reads `/sitemap.xml` (following a sitemap index) and visits every page, home page first, then the pages the home page links to (menus and section pages such as category archives, which sitemaps often leave out; up to 200, same site only, no feeds, files or query strings), then in sitemap order. The work rides on real traffic: after the site answers a request, the Worker claims a few queued pages and visits them in the background through its own `SELF` service binding, so the warm-up runs where readers and crawlers are (with Smart Placement, near the database) and fills that region's cache tiers. Cron Triggers run in whatever data center has spare capacity, often on another continent, and placement hints don't apply to them, so they're only the fallback: as caching gets better, fewer requests reach the Worker (a cache hit never runs it), so an hourly task (`page-cache-warm`, on the site's hourly Cron Trigger) takes up to 8 warm steps in a row while they make progress, so a run, a re-warm after edits or the daily refresh never waits for a visitor. With nothing to do it reads the progress row and stops. Its visits may render far from the database (slower, still within each visit's deadline); Workers Cache's upper tier, which every data center consults, gets the pages either way. It does nothing while warming is off. On a site updated from an earlier version it's scheduled the next time the Features page opens or warming is turned on. Batches are claimed atomically, so parallel isolates never repeat pages; a new clear or deploy restarts the run. The run's URLs are stored once (`plugin:coywolf-pack:pageCache:warmQueue:<run>:<n>` option rows of up to 500 URLs, removed when the run finishes or a new one starts; a batch claimed and never recorded, because its isolate stopped, counts as failed after two minutes so the run still finishes) and each claim only updates a small progress row, so even a 5,000-page run writes little per batch. Pages whose render used a stopgap (a video poster still being copied to the media host, see **Posters from your media host**) aren't left cold: the warmer's render of such a page isn't cached (the middleware answers it with an internal `X-Coywolf-Stopgap: 1` header, which is never stored in the cache, so visitors don't see it), and the page is listed in the progress row (up to 200, same site only) and visited again once the rest of the run is done and 20 seconds have passed, by which time its posters are copied, so it's cached with the normal lifetime. A page still on a stopgap is tried at most twice more, then given up on (it's counted, the run still finishes). The list belongs to its run: a new clear or deploy starts over. The page shows progress ("Re-warming N pages after their video posters were copied" while revisits are pending), and **Warm now** starts a run by hand. Needs a `services` binding named `SELF` pointing at the Worker itself. A page that hangs can't hold the warm-up: each visit (the fetch and reading the page) is cut off after 8 seconds and counts as failed, logged once with its URL (`coywolf-pack: warm visit timed out after 8000 ms: <url>`); a warm step stops claiming pages early enough to finish within 24 seconds and ends then whatever happens (`coywolf-pack: warm step timed out`), well inside the 30 seconds Cloudflare gives background work; a sitemap read that times out leaves the collect step to be tried again two minutes later instead of failing the run. Alerts can key on those log lines.
- **Warming after content edits**: EmDash clears cached pages by tag when content, menus, taxonomies, widgets or site settings change, and list pages carry their collection's tag, so saving or publishing one post clears the home page, the category archives and many posts. With warming on, the pack middleware notices those clears (it wraps the request's `cache.invalidate`, so it fires exactly when EmDash clears something, through the admin, its API or MCP; draft saves that don't change live content clear nothing and start nothing) and starts a run a minute after the last such write: each write pushes the start back a minute, up to five minutes after the first, so a burst of edits makes one run. The schedule is a `rewarmAfter` time in the progress row; the next warm step after it starts the run (reason "edit"), replacing a run still under way (pages it already warmed are cache hits, so they cost little). The Performance page shows "Content changed: warming again at about …" meanwhile. The warmer's own visits are GET requests, which never schedule a run.
- **Daily refresh**: Cloudflare doesn't keep every page for its full cache lifetime; pages that aren't requested often are dropped from a data center's cache early, so a search bot crawling older posts, or a visitor arriving from a search result, would wait for those pages to be built. With warming on, a run also starts once a day: the first warm step more than 24 hours after the last run finished (whatever started it) starts a new one (reason "daily"; on a site with no run yet, the first page view starts one). It visits the same pages in the same order as any other run; pages still cached come back as cache hits and cost little (no database queries), so only the pages Cloudflare dropped are built again. A deploy, clear, edit or **Warm now** run resets the clock, since the next refresh is due a day after the last run finished. The due time comes from the progress row's `finishedAt`, which requests already have with the feature switches, so requests in between still skip the warm step without a query, and the run starts through the same atomic claim as the others, so parallel isolates start it once. The Performance page shows "Next daily refresh: about …" while warming is idle. The refresh is on by default; uncheck **Refresh daily** under Cache warming (setting `pageCacheWarmDaily`, read with the other switches, so it adds no query) to turn it off: no daily runs then (and no first run on a site that has none), while deploys, clears, edits and **Warm now** still start runs.
- **Scoped clearing**: saving settings that don't change pages (backups, the link report, the Performance page's media and warming controls) clears nothing; redirect edits (including resolving removed content, imports, and a database rewind or undo) clear only cached redirects (tag `coywolf-redirects`, cleared again about five minutes later like other saves); robots.txt rules clear only `/robots.txt`; a Stream webhook call clears only the pages that embed its video, and records no settings change (no settling clear, no re-warm). Everything else clears every page.
- **Clear pages and images**: clears every cached page and redirect now, plus the media host's images (originals and resized copies) from the zone cache. Cloudflare's zone **Purge Everything** doesn't reach Workers Cache, which belongs to the Worker. Clearing images uses the Clean Image URLs token, which needs **Zone → Cache Purge → Purge**.
- **Pages rendered after a failed read aren't cached**: when the pack can't read what it needs (D1 unreachable for a moment, a query error), it fails closed for that request. The feature switches fall back to their defaults (most are off), settings read as unset, redirect and robots.txt rules as absent, and a module whose page metadata failed (or ran into EmDash's 5-second hook timeout) adds none. The page still goes out, but without its schema, reviews, videos or redirects, so it isn't put in the edge cache, where it would stay for the Page cache lifetime. The next request renders it again. Each such fallback is counted (`noteReadFailure()` in `src/core/read-failures.ts`). The middleware compares the count before the request and after the response has rendered, and turns route caching off (`cache.set(false)`) when it moved. For a cacheable HTML page, that happens after the page is read in full: Astro streams pages, so a component can still read settings, or call `cache.set()` (which would turn caching back on), after the headers are ready. The log says `coywolf-pack: GET /path/ not edge-cached: a read failed while it rendered (last failure: …)`, naming what failed (for example `schema: page:metadata`). A module that fails on every render (a bug rather than a blip) keeps every page out of the cache until it's fixed, so a steady stream of these lines means something to fix, not a D1 problem. A plugin route answering "not found" (a feature that's off, or the plugin not enabled) isn't a failure; only server errors are. The count is per isolate, so a failure while another page renders at the same moment keeps that page out of the cache too, which only costs one render. A failed read is never remembered as the answer: the switches, the schema configuration, a page's reviews and discovery files are read again on the next request.

Responses the pack serves itself (files, clean image URLs) keep their own `Cache-Control`: the middleware turns Astro's route caching off for them, so a site route rule (for example on a catch-all page route) doesn't add its edge lifetime to them. The ones below set their own edge caching instead, and redirects too (see [Redirects](redirects.md)).

**Server-Timing.** A page going to the edge cache loses the `Server-Timing` set by the time the pack's middleware returns, and the pack's own edge-cached answers (live search) send none, so the edge doesn't hand one render's timings to every later visitor. EmDash adds its own `Server-Timing` (`setup`, `rt`, `render`, `db.*`…) in its middleware, which runs outside the pack's and after it, so the pack can't remove it: cached pages still carry the timings of the render that filled the cache. Removing those needs a change in EmDash (or a Worker entry point of the site's own that strips the header from cacheable responses).

### Pack files at the edge

| URL | Edge lifetime | Tags (cleared by) |
| --- | --- | --- |
| `/robots.txt`, `<path>/robots.txt` (a small 404) | a day | `coywolf-robots` (robots.txt rules, EmDash SEO saves) |
| Live search client (`…/search/live-client?v=<hash>`) | a year for the current hash, 5 minutes otherwise | none needed (a new pack version changes the URL) |
| Live results (`…/search/live`) | 5 minutes | `coywolf-search` and the searchable collections (EmDash's content purges) |
| Title index (`…/search/index?v=<version>`) | a day for the current version, 5 minutes otherwise | `coywolf-search` and the searchable collections |
| `/feed/` and term feeds | an hour | `coywolf:feed`, its collections and taxonomies |
| `/llms.txt` | an hour | `coywolf:llms` and its collections (and a rebuild that changes it) |
| `<entry>/index.html.md` | a day | `coywolf:markdown`, the collection and the entry id |
| `/news-sitemap.xml`, `/coywolf-news-sitemap.xml` | 5 minutes | `coywolf:news` and its collections (and a rebuild that changes it) |
| `/coywolf-video-sitemap.xml` | an hour | `coywolf:video-sitemap` (a change to a listed video) and its entries' collections |
| Redirects and 410s | 30 days | `coywolf-redirects` |

Every one of them also carries the settings generation's tag (see **After Coywolf Pack settings change**), and a pack save that changes pages clears them with everything else. Only successful answers go to the edge: errors, rate-limited answers and anything rendered after a failed read never do, and nothing that varies per visitor is cached (EmDash keeps anything rendered for a signed-in user out of the edge cache).

### robots.txt and the live search script at the edge

Crawlers ask for `/robots.txt` constantly, and each answer used to run the Worker. It's now kept in the edge cache for a day, whether the pack's Robots.txt Rules or EmDash's own file serves it (tag `coywolf-robots`; the pack clears its cache after its admin saves and settings changes, so edits show at once). A `robots.txt` asked for below the root (`/news/robots.txt`, which crawlers try) gets a small plain-text 404, also cached for a day, instead of a rendered 404 page. The live search client (`/_emdash/api/plugins/coywolf-pack/search/live-client?v=<hash>`) is kept at the edge for a year when the URL names the current version (5 minutes otherwise); live results and the title index are kept for minutes to a day (see the table above).

### Rate limiting

Search (when **Search rate limit** is on), video plays and video likes count each visitor's requests. Without help they count per Worker isolate, and Workers spread one visitor's requests over many short-lived isolates, so a client that's spread out is barely limited. Add a [Workers Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) binding named `COYWOLF_RATE_LIMITER` and the pack uses it for all three, with no other setup: Cloudflare counts across isolates in each location. For coywolf.com:

```jsonc
// wrangler.jsonc
"ratelimits": [
  // Coywolf Pack: search, video plays and likes, per visitor (IPv6 by /64). namespace_id is unique per account: one per site.
  { "name": "COYWOLF_RATE_LIMITER", "namespace_id": "1001", "simple": { "limit": 120, "period": 60 } }
]
```

- Each limit has keys of its own (`search:…`, `play:…`, `like:…`, from a salted hash of the address, never the address), each counted at the binding's limit (120 a minute here).
- Visitors are keyed by IP address; an IPv6 address by its /64, since one connection gets a whole /64 (2^64 addresses to rotate through).
- Search: the binding replaces the per-isolate counter (`requestsPerMinute`), which stays as the fallback without a binding or if the binding errors. Plays and likes keep their stricter per-isolate limits (10 and 20 a minute) and the daily cap on new likes, and the binding adds the limit across isolates.
- A binding with another name: `coywolfPlugin({ search: { rateLimiter: "NAME" }, videos: { rateLimiter: "NAME" } })`.
- Without a binding nothing changes: each isolate counts on its own, best effort.
- Requests answered from the edge cache (repeat searches) never reach the Worker, so they aren't counted; only misses are.

### Cloudflare usage

The Performance page's **Cloudflare usage** card, and a **Cloudflare usage** dashboard widget, show what the site and its account use on Cloudflare, read from Cloudflare's analytics and kept for an hour (**Refresh** reads again):

- **The estimated bill**: Workers Paid's $5 a month plus anything over the included amounts, worked out from the account's last 30 days (allowances are shared by every Worker and database in the account). On Workers Free it compares today (UTC; the limits reset at 00:00 UTC) with the daily limits instead.
- **The account against its plan**: Workers requests and CPU time, D1 rows read and written, and D1 storage, with the share of each allowance. The plan is read from the account's entitlements (D1's per-database size limit is 10 GB on Paid, 500 MB on Free); without them, a day over Free's limits shows the account is on Paid, and otherwise Paid is assumed.
- **This site**: its Worker's requests and CPU time and its D1 database's rows read and written, queries and size, for today, the last 7 days and the last 30 days (UTC dates, including today). The Worker is the one whose current deployment runs this version (the `CF_VERSION_METADATA` binding), and the database is the D1 binding named `DB` in that Worker's settings, so nothing is configured per site.
- **Cache warming (estimate)**: the warmer's visits over the last 7 days from Workers Logs, as a share of the site's requests and CPU time, and its D1 rows read (the site's total times that share). Logs are sampled, so it's labeled as an estimate.

It needs a read-only, account-owned API token (Cloudflare dashboard → Manage Account → Account API Tokens → Create Custom Token):

- Account → Account Analytics → Read (D1 and Workers usage)
- Workers → Metadata Read-Only, for All Workers (finds the site's Worker and database, and reads Workers Logs for the warming estimate; on a personal token: Account → Workers Scripts → Read and Account → Workers Observability → Edit)
- Account → Account Settings → Read (the plan, from the account's entitlements)
- Optional: Zone → Zone → Read, for all zones or the site's zone, so the Discovery page can show whether [Crawler Hints](discovery.md#crawler-hints) is on

Set it as the `USAGE_API_TOKEN` Worker secret (one token works for every site in the account), or save it as **Cloudflare usage** on the plugin's Settings page. The account comes from `CF_ACCOUNT_ID`, the Clean Image URLs account ID, or the token itself when it's limited to one account. A part the token can't read is left out with a note naming the permission; the rest still shows.
