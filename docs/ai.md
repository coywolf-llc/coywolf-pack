# AI Enrichment

[Coywolf Pack documentation](README.md) · [Getting started](../README.md#getting-started)

Ported from Coywolf SEO's AI features, with the same prompts and validation:

- **Entities for schema** (`ai.entities`). The model lists the people, organizations, places, and things a page is about, without identifiers. Each name is looked up on Wikidata (`wbsearchentities`), and only items whose label or alias is that name (ignoring case, accents, and punctuation) count. When several match, the model may only pick one of them. Each chosen item's `instance of` (P31) claims are then checked (one Wikidata Query Service request per entry for all its items): disambiguation pages are dropped, a Person must be human, an Organization or Place can't be a creative work (the album instead of the band), and an Organization can't be a place. The JSON-LD `name` is Wikidata's label. The result is stored per entry as Schema.org `about` (main subjects) and `mentions`, each with `sameAs` links to Wikidata, Wikipedia, and the official website (P856) when there is one. Coywolf's Schema module reads them with `getEntryEntities(ctx | db, collection, id)` from `src/ai/entities.ts`.
- **glossary.io definitions** (`ai.glossary`, on by default). When an entity's Wikidata ID has a definition on [glossary.io](https://glossary.io), its node gets that page last in `sameAs` (for example `https://glossary.io/gemini/`), the glossary's short definition as its `description` (the stored description stays when there isn't one), and since 0.46.0 glossary.io's names for it other than the entity's own as `alternateName` (the term's glossary name and its "Also known as" names: X gets "Twitter", Wikidata's "search engine optimization" gets "SEO"). glossary.io lists every term with a Wikidata ID in one index, `https://glossary.io/api/entities.json` (`{v: 1, terms: {QID: [slug, definition, names]}}`, about 1,000 terms, 80 KB compressed). The site stores a copy in plugin storage (`aiGlossary`, document `index`), and each isolate keeps it in memory for an hour. glossary.io is asked only when the site has no copy yet (the first render that needs it waits up to 1.5 s, so pages don't go into the edge cache without it) and, after the response, when the copy is a day old: about one request a day per site, and none on days nothing renders. If glossary.io fails, the page renders with the copy it has (or without glossary data) and stays cacheable; that isolate tries again after 10 minutes, then 20, 40… up to a day while it keeps failing, logging each failure. An answer with no terms counts as a failure, so it never replaces a good copy. Requests carry `User-Agent: CoywolfPack/<version>`. Pages already in the edge cache pick up changes when they render again. It's never used on glossary.io itself. With a D1 database instead of the plugin context (`getEntryEntities(db, …)`), only a copy the site already stored is used. A copy stored by 0.45.0 (no names) is refreshed after the first response that needs it. Code: `src/ai/glossary.ts`.
- **glossary.io links** (`ai.glossaryLinks`, off by default; since 0.49.0). After an entry's entities are found, each one with a glossary.io definition gets one link to it in the entry's text, and the entry is republished. It runs after a first analysis and after one whose text changed since the links last looked, never after a re-analysis for new settings. Entries analyzed before the part was turned on are linked with **Link existing entries** (below); without it, their first text change after the part is on only records their text (it can't be told apart from a re-analysis for new settings), and the next one links. The rules (`src/ai/glossary-links.ts`):
  - An existing glossary.io link to the term: nothing to do. Otherwise the first link whose text is one of the entity's names (its Schema name or glossary.io's names for it, ignoring case and hyphens; a plural only for concepts and abbreviations) is switched when it's an identity link: the entity's Wikipedia article or Wikidata item, a site's home or about page, its official site (a deeper page only when the path names it, like `yoast.com/wordpress/plugins/seo/` for Yoast SEO), a social profile, or a page on a site named after it (`apple.com/apple-music/`).
  - Never switched: links to the site itself or its other domains, affiliate links (`/visit/…`, `/ref/…`, affiliate networks and short links, referral parameters, fragments and landing subdomains like `try.` and `go.`), citations (docs, help and sign-up subdomains, articles, issues, dated or deep paths, queries and fragments), a Wikipedia link on a claim rather than the name, a link whose text is a domain ("create an account at mastodon.social"), a name inside a longer name ("Shopify" in "Shopify Unite"), and a profile link in a list item.
  - An entity named by an affiliate link gets no glossary link in that entry, so nothing competes with the affiliate link: when the link's text is the entity's name, or mentions it and the link is for it (its brand matches, like `shopify.pxf.io` for "Shopify free", or the destination is unknown, like an Amazon short link). "Pressable WordPress hosting" doesn't rule out WordPress.
  - Otherwise its first plain mention in a paragraph or list item is linked, with the text as written ("Progressive Web Apps", "filler words") and the possessive right after it ("Google's", below). Not in headings, blockquotes, code, other links, handles, paths or domains, not part of a longer name ("Google" in "Google Search Console" or "Google I/O", "SMTP" in "Gravity SMTP", "Mail" in "Big Mail"), and not an abbreviation right after a different expansion ("neuro-linguistic programming (NLP)"). A mention at the start of a sentence or inside quotation marks is used only when there's no other.
  - **Possessives** (since 0.51.0). A word with a possessive is linked whole: "Google's" and "Anthropic’s", never "Google" followed by an unlinked "'s". A possessive is `'s` or `’s` before a space, punctuation or the end of the paragraph, or, after a name that ends in s, a bare `'` or `’` ("Threads’ growth"). The letter apostrophe `ʼ` counts like `’`, and `'S` counts only after a name in capitals ("GOOGLE'S"). Not a possessive: `'s` right before a letter, a digit or a hyphen ("Google’sfoo", "'s5", "'s-Hertogenbosch"), and a bare apostrophe that could be a closing quotation mark or part of code, which is one inside a quotation of any kind (`'`, `‘`, `“`, `"`) opened earlier in the paragraph and not closed ("‘Threads’"), or after a name that comes right after `=`, `/` or a quotation mark. A possessive formatted as code is left alone. New links are made that way. A link that's switched keeps the text its author linked, and then gets the possessive after it like every other glossary.io link: each run (after an analysis, on a retry, and with **Link existing entries**, dry run included) also moves the possessive after any glossary.io link in the entry inside the link, whether the part made it, switched it, or a person made it, in any block. It's published with the same safety as a new link, and `keepDates` applies. Only the link's marks change, never the text, and links to other sites are never touched. A possessive with other formatting than the link (bold, say) keeps it. A block the fix can't read (a span whose marks aren't a list) is left as it is, and never stops the entry's links. Such a fix doesn't count as linking the term. An entry whose only changes are fixes like this ends "linked" too, with each one listed as a `possessive` change (with the term's Wikidata ID when the site's copy of the index knows the link's slug). Entries on the `skip` list are left alone.
  - What it remembers is kept per entry in its own storage collection (`aiLinks`), so a failed analysis or a trash and restore doesn't erase it: the Wikidata IDs it handled (each entity is linked at most once per entry, and a link removed by hand isn't added back), the text it last saw, links to deleted terms still to take out (`unlink`), and when to try again. While an edit is in progress it also keeps a marker, and with `keepDates` the date to put back (`keepUpdatedAt`).
  - Safety: only published entries with no pending draft and no save in the last two minutes are edited; the entry is read again right before the write and left alone if anyone saved it; only the draft the edit made is published. Entries it had to leave (a draft, a recent save, a save in between, no glossary.io index yet, an error) are tried again by the scheduled run after 30 minutes, then 1, 2, 4, 8 and 16 hours, without a model call. If a save lands in the moment between the read and the write, nothing is published and it's logged as an error: check that entry's revisions. An edit whose publish didn't happen is recognized and published on the next try (an unpublished removal of links to a deleted term only while that part is on and the term is still confirmed gone; otherwise its draft is left for you to publish or discard, and that's logged).
  - Site settings, in `coywolfPlugin({ ai: { glossaryLinks: { … } } })`: `ownHosts`, the site's other domains, never switched (the site's own host always counts; `"coywolf.*"` is every coywolf domain and its subdomains); `shortHosts`, the site's affiliate short-link domains (`["coywolf.io"]`); `skip`, entry slugs never linked (legal pages, link directories; `"posts:slug"` for one collection); `keepDates` (below).
  - **Keep dates** (`keepDates: true`, off by default; since 0.50.0). Publishing moves an entry's updated date, which the theme's Updated line, Schema `dateModified`, the sitemap and feeds show. With `keepDates`, right after the part publishes its own edit (after an analysis, on a retry, with **Link existing entries**, or when it removes links to deleted terms), it puts the entry's updated date back in D1 and clears the entry's cached pages, right away and once more about 20 seconds later (a page rendered in between could have been cached with the new date). It changes only the row its own write left, as EmDash returned it (same date, same version, its revision live, no draft) and never reads the entry again in between, so a save anyone made in between or right after keeps its date. A site that uses EmDash's object cache (`objectCache`, for example `kvCache`) can keep showing the publish-time date until that cache's copy expires; the pack doesn't clear it. The version number stays as the publish set it, so an editor's open tab still sees that the entry changed. Edits that end "staged" or "collided" keep the new date. It needs the site's D1 binding (`DB`); without it, the edit is still published and an error is logged once. Code: `src/ai/keep-date.ts`.
  - **Link existing entries:** `POST /_emdash/api/plugins/coywolf-pack/ai/glossary-links` with `{ keys: ["posts:<id>", …] }` (up to 25; 5 at a time is gentler, since each publish runs every module's publish hooks) or pages of analyzed entries (`{ limit, cursor }`) runs the same code. `dryRun: true` plans without writing (allowed with the part off); each result lists its changes (`add`, `switch`, or `possessive`). `exclude: { "posts:<id>": ["Q123"] }` names entities never to link in an entry. It answers 409 while the scheduled AI run is working; try again a minute later. Each publish moves the entry's updated date unless `keepDates` is on. Code: `src/ai/glossary-linker.ts`.
  - **Possessives only** (since 0.51.0): add `only: "possessive"` to fix the possessives after the glossary.io links entries already have, and nothing else: `{ keys: ["posts:<id>", …], only: "possessive", dryRun: true }` lists the fixes, and the same without `dryRun` publishes them. This is how you fix existing links after updating to 0.51.0 without linking anything new. No link is made or switched, however many definitions glossary.io has by now; `exclude` is ignored; and what the part remembers about the entry (the entities it handled, the text it last saw, a retry that's waiting) stays as it was. Like a normal run, it skips an entry that has no successful analysis (`skipped`, "not analyzed"), dry run included: publishing such an entry queues its first analysis, and a first analysis links. An entry analyzed before 0.51.0 gets its text hash first (see **Analyses made before 0.51.0** below; a dry run only checks that it would), so the fix's publish can't queue a re-analysis. An entry whose publish would queue an analysis is skipped, dry run included, and nothing is published or written. The reasons a possessives-only run gives for `skipped`:
    - "not analyzed": the entry has no successful analysis.
    - "on the skip list": its slug is in `skip`.
    - "text hash not recorded (…)": it was analyzed before 0.51.0 with other settings than today's, and its text hash can't be recorded, for the reason in the brackets: `queued` (an analysis is queued), `draft` (a pending draft), `recently saved` (a save in the last two minutes), `unpublished`, `title changed` (another title than the analyzed one), or `changed meanwhile` (its analysis changed during the run).
    - "text changed since its analysis": its title or text isn't what was analyzed, and no analysis is queued (it changed while AI Enrichment was off, its collection wasn't covered, or the queue was cleared). Analyze it first (**Run bulk**; that analysis links it, like any text change), or link it with a normal run.

    A run on glossary.io itself, or on a site whose URL isn't known, skips every entry, as a normal run does. The fixes are published with the same safety as any link edit, and each publish moves the entry's updated date unless `keepDates` is on. A possessives-only run only moves possessives, and finishes only its own kind of unpublished edit (one that moved possessives and made no link). Anything else of the part's that's unfinished on an entry is left exactly as it was, unpublished and with nothing remembered or forgotten, and the entry ends `draft`: an edit with new or switched links waits for a normal run, and a removal of links to a deleted term waits for the removal's own turn. A possessives-only run schedules no retry (a retry links): run it again for entries that end `draft`, `busy`, `conflict`, `staged` or `error`. It writes what the part remembers only when its own edit changed it, and then only that edit's marker, over what's stored at that moment. One that fails leaves nothing behind that could link the entry later: for an entry the part remembered nothing about, either nothing is remembered afterwards, or what's left (a marker for an edit that was saved but not published, which the next possessives-only run finishes, or a memo that couldn't be deleted) is marked as nothing remembered, and the entry's next analysis never takes it for a text change. The same mark is on what a removal of links to a deleted term remembers for an entry the part knew nothing about, so that entry's next analysis doesn't link it either.
- **Remove links to deleted glossary.io terms** (`ai.glossaryLinksRemoveGone`, off by default, needs glossary.io links; since 0.50.0). When a term is gone from glossary.io for good, its links come out of the site's entries and the text stays. It only checks whether definitions exist: it compares the site's copies of glossary.io's public index and asks for a term's public JSON (`https://glossary.io/api/terms/<slug>.json`) only to read the status code. It never sends anything to glossary.io. A term counts as deleted only when all of these are true:
  - It's missing from the index. A term whose Wikidata ID is still there under a new slug was renamed: its links stay (glossary.io redirects them). A slug that another term has now (another Wikidata ID) stays linked too, since the address leads to a definition again.
  - glossary.io answers 404 or 410 for it twice, at least 20 hours apart. Errors, 403, 429 and timeouts don't count: the term is asked again an hour later, then after 2, 4, 8 and 16 hours, then once a day, and after two weeks of nothing else it's dropped (logged; its links stay). Any 2xx or 3xx answer means it's still there.
  - It's missing from two copies of the index fetched at least 20 hours apart.

  So the fastest removal is about a day after a term goes, and a glossary.io outage or a mistake fixed within a day removes nothing.
  - **Holds:** a copy of the index that lost more than 5 terms at once, or more than 1% of them when that's larger, is refused, and nothing is removed until a later copy has them back or a person decides. More than 5 terms deleted at once, or links in more than 20 entries, also wait. Only terms that aren't past these limits yet count toward them: once a term is under them, or you chose **Remove their links**, it stays approved until its links are all out, so the same terms never ask twice. Each hold logs an error and shows on the AI Enrichment page, with **Remove their links** (for a refused copy, **Check them one by one**, which still needs the two answers above) and **Keep the links**. Kept links are never removed unless the term comes back and is deleted again.
  - **Which links:** the ones in published entries of the collections AI Enrichment works on, whether the part made them or a person did. Entries on the `skip` list are left alone. The links are taken out by the same scheduled pass that retries glossary.io links, three entries at a time, with the same safety as linking: no pending drafts, no saves in the last two minutes, only its own draft published, and `keepDates` applies. Right before each edit it checks again that the term is still missing (its Wikidata ID and its slug). Once the links are out, the term can be linked again if it comes back. A removal never links anything by itself. Only when a try to link the entry was already waiting (your site asked for it by setting the entry's `retryAt` in `aiLinks`, or a link had to wait for a draft) is the entry checked for new links a few minutes later, so the removal doesn't use that try up. Entries are looked for 5 terms per scheduled run (one D1 query per Portable Text field each, counted in the run's budget), and again every 6 hours until none links to the term.
  - The first run only records the current index, so terms that were already missing when you first turned it on are never removed. After it's been off for more than two days it starts over from the current index the same way, so terms that went missing meanwhile are never removed either; a break of under a day always counts as if it had stayed on (terms that went missing meanwhile are checked like any other), and between one and two days it can go either way. What it tracks is in plugin storage (`aiGlossary`, document `gone`). The status and the decisions are also on `POST /_emdash/api/plugins/coywolf-pack/ai/glossary-links`: `{ gone: "status" }`, or `{ gone: "approve" }` or `{ gone: "dismiss" }` with `slugs` (a hold's whole list, as shown). Code: `src/ai/glossary-gone.ts`.
- **Output entities on their own** (`ai.entitiesStandalone`). Adds the entities to the page's JSON-LD as a `WebPage` node (same `@id` as EmDash's `mainEntityOfPage`). Only for sites that don't use Coywolf Schema.
- **Meta descriptions** (`ai.descriptions`). Writes a description (under 155 characters, no clickbait) for published entries in SEO-enabled collections that don't have one. By default they're suggestions you edit and apply on the AI page; or have empty descriptions filled automatically. Either way it writes only EmDash's SEO panel field and never replaces a description someone wrote unless you choose **Replace**.
- **Image text** (`ai.imageText`). Writes alt text (and, if you turn it on, captions) for images on upload and in bulk, with accessibility-first prompts. When the image is used in a published entry (EmDash's media usage index, EmDash 1.5+), the model also gets that entry's title, the heading above the image, and about 900 characters of text on each side with the image's place marked, so the alt text and caption fit how the image is used there while still reading well on their own (about 450 more input tokens per image). Only published entries' text is sent; an image that isn't used in one is described on its own. An image analyzed on upload isn't in an entry yet, so it's described on its own; **Run bulk** (or **Analyze again**) after it's published gives it the article's context. Alt text and captions people wrote are kept unless you turn on overwrite. EmDash media has no title or description fields, so titles are shown on the AI page for reference only.

Apart from glossary.io definitions, they're all off by default, under the **AI Enrichment** switch on the **Features** page (**Coywolf Pack → Features** in the sidebar).

**In the entry editor.** While AI Enrichment is on, a saved entry's sidebar has an **AI suggestions** section (admins only): the **AI Enrich** button (below), the suggested meta description with **Copy** and **Dismiss**, the entities found (main subjects highlighted), and **Analyze again**, which queues the entry. The suggested description shown there isn't written from that section: paste it into the SEO section, or apply it on the AI page. Only **AI Enrich**'s review fills an empty one, through the editor itself. The section says so when the entry's collection isn't one AI Enrichment analyzes. An entry the **AI Enrich** button analyzed shows "Analyzed in the editor, waiting for publish" there until it's published.


## AI Enrich button

Since 0.52.0, the **AI suggestions** section of a saved entry's sidebar has an **AI Enrich** button (admins only), so an entry gets its glossary.io links, image text and meta description before it goes live, and you see them first. It needs EmDash 1.6 or later, which gives the pack's sections the editor's unsaved values, and nothing to set up. It shows while AI Enrichment is on, the entry's collection is one AI Enrichment works on, and **glossary.io links** (with **Entities for schema**) or **Image text** is on. The line under it says what a click adds and which AI provider gets the entry's text and images. Without an API key, a click says so.

**What a click does.** It reads what's in the editor now, saved or not, and works on that. Drafts that were never published work too (the section shows on saved entries only):

- **glossary.io links** (when the part is on): the entities are found the way an analysis finds them (or taken from the entry's analysis, or an earlier click's, when the title and text are the same), and the links are planned by the same rules as after publishing, possessives included. A link you took out by hand isn't added back: one removed after an earlier analysis, or one you took out of an applied proposal before clicking again. Entries on the `skip` list get no links.
- **Image text** (when the part is on): every image in the entry's rich text and image fields (image blocks, galleries, and image fields such as a featured image) that has no alt text or no caption gets it. The text comes from the media library item first, then from a suggestion the pack already has for that image, and only then from the model, which also gets the draft's title and the text around the image. Text a person wrote is never replaced, an image whose suggestion you dismissed is left alone, and SVGs, images added by URL and images from another media provider are skipped. Captions are filled whatever **Also write captions** says; that setting and the image text mode still decide what's written to the media library itself, as on upload.
- **Meta description** (when **Meta descriptions** and **glossary.io links** are on, the collection has an SEO panel and the SEO panel's description is empty, including one you cleared and haven't saved): one is written with the links' analysis and offered in the review. A description in the SEO panel, saved or not, is never replaced. One you dismissed on the AI page (or that was applied and you removed since) isn't offered again while the published title and text stay the ones it was written for; once the text changes, a new one is written and offered.

**The review.** Nothing in the editor changes until you choose. When the answer is in, a **Review AI Enrich changes** dialog lists exactly what would change:

- **Links**: each term with its glossary.io address, and how many possessives move inside their link. A link you already have (to the term's home page, Wikipedia article or profile) that would be switched to glossary.io says "your link switched to", and the heading counts new and switched links apart ("Links (2 added, 1 switched)").
- **Images**: each image's file name with the alt text and caption it gets (only what's added), and how many images are left as they are, and why.
- **Meta description**: the text, with **Fill the meta description** (on). EmDash's SEO panel saves it about half a second after **Apply changes**, outside the entry's revisions, so on a published entry it's live at once. Turn the box off to leave the SEO panel alone.
- What stopped it, when something did (today's call limit, Wikidata asking to slow down, an AI service error, no copy of the glossary.io index yet): the rest of the review is what could still be done.

**Apply changes** puts it all in the form as an unsaved change; then save or publish as usual (the editor's autosave saves it too). The rich text field redraws with the links, so its cursor position and undo history start over; EmDash keeps the draft revision it replaced in the history. **Cancel** (or Escape) changes nothing, and the analysis stays for the publish (below). A click outside the dialog doesn't close it.

**When the entry changes meanwhile.** Typing, or any other change to the form, the slug or the SEO text, while it works or while the review is open makes its answer stale: "The entry changed while AI Enrich worked, so nothing was applied." **Run again** reads the editor again. What that costs: image text is always reused (it's saved per image); the entity analysis is reused when the title and text are the same (a changed slug or SEO text costs nothing to redo), and is paid for again when the text itself changed. The same goes for a wait: when the entry changes while the button waits to ask again, nothing more is sent. A review is only for the editor it was made in: after you leave the entry and open it again, or edit it while the settings are hidden, the review doesn't open, and **Run again** is offered instead. While a version from the history is open, or the entry is locked, the editor takes no changes: close it, then choose **Apply changes** again.

**Time.** A click usually takes 20 to 40 seconds. Each request to the site is built to answer within about 85 seconds, inside the 100 seconds after which Cloudflare gives up on a request: no model call starts after 25 seconds (an image's is checked again once its file is read, and no file is read after that), each call gives up after 40, and saving the result can wait up to about 10 seconds for the scheduled run. Only a media file that takes very long to read can stretch that; the request's work is saved as it goes either way. When only time or the limit of 8 images per request stopped it, the button asks again on its own, up to 6 times per click, only while the entry is unchanged, and never more than 10 minutes after the click; each request starts where the last one stopped (the Wikidata lookups too), and you get one review at the end ("Working… 8 of 12 images done."). A request that ran out of time without getting anything new doesn't ask again: it says so. A post with twelve images without alt text takes two requests. Every call counts against the daily limit and is in the usage log.

**Lost answers.** What a request pays for is saved as soon as it's paid (the entities, a description, each image's text), so a request that fails halfway, or whose page was closed, loses none of it: the next one reuses it, and so does the publish. When an answer doesn't come (a network error, or none within 95 seconds), the button says "Still checking…" and asks once more, then "AI Enrich didn't finish. Click again: what was already paid for is kept." When the site refuses the request (you were signed out, your role no longer allows it, or the plugin was turned off), the button shows the site's message and doesn't ask again. One request runs per entry at a time. While another holds the entry (another tab, or a request whose connection was lost), the button waits 10 seconds and asks again, up to 6 times. A request whose page was closed frees the entry within about 50 seconds: its work can go on for up to 30 seconds after the page is gone, and its lock lasts 20 seconds past that. The lock is never renewed past 110 seconds. A call that fails or times out may still be billed by the AI provider. **Hide settings** doesn't stop a click: show the settings again and the section shows it, or its review. A message from a click that ended ("Added. Save or publish as usual.", an error) goes when the section is hidden, and at the next save once it's 10 seconds old.

**Size.** The whole draft is sent as JSON, up to 2 MiB (2,097,152 bytes). The button measures it before sending: a larger draft isn't sent at all, and the button says "This entry is too large for AI Enrich (over 2 MB)." The route declares the same limit to EmDash, which refuses a larger body itself (HTTP 413). There's no other size limit: a long post is patched whole.

**Privacy.** The entry's text and images go to the AI provider when you click, and the names of the entities found in it to Wikidata's search, before the entry is published. Nothing is sent until you click.

**At publish.** The button's analysis is kept apart (`aiDrafts`) until the entry is published, so the live page's JSON-LD keeps the published entry's entities meanwhile. When the published title and text are the ones the button analyzed (with its changes or without them), the publish uses that analysis: nothing is queued and no model is called. When that analysis lacks something (the click stopped early, its description failed, or **Meta descriptions** was switched on since), the entry is queued as usual and its analysis pays only for what's missing; so does a publish made while a click was still running, including what that click finishes after the publish. An analysis the button made with another provider or text model than today's is never used: the entry is analyzed as usual. **Analyze again** always pays for a fresh analysis, whatever the button staged. EmDash's own save of the SEO panel, half a second after **Apply changes**, isn't that publish: nothing the button staged or planned is used or settled by it, and nothing that still waits for a publish is deleted (in a collection without revisions, where a save is the publish, the same holds until the saved text has the button's changes). Only an analysis the button staged for exactly the text that's live goes, once the entry's own analysis is of that text under today's settings: it has nothing left to wait for. When that save queues the entry (it had no analysis of its text yet), the scheduled run takes what the button paid for instead of paying again, also when a bulk run had queued the entry before. A meta description the review filled counts as applied at the publish (a suggestion from the entry's own analysis that the review filled, as soon as the SEO panel saves it); when the entry has another description by then (yours), yours stays and the button's is recorded as dismissed; with the box off it stays a suggestion, as from an analysis, and with **Fill empty descriptions automatically** it's written by that scheduled run a few minutes after the publish, not seconds after it while you may still be in the editor. When the text changed since the click, the entry is analyzed as usual. The links the button proposed never count as linked when you click, only as planned. At the publish, when the published text has any of them (or the button proposed none), they count as linked, so one you removed before publishing stays removed; then the scheduled run checks the entry's links once, a few minutes later, without a model call, and adds only what's missing (so changes you didn't apply are linked then, with `keepDates` if it's on). Planned links count only on your own publishes (the pack's link edits don't settle them) and for 30 days. An analysis that's never published is deleted after 30 days, and with its entry.

## How it runs

Saving, publishing, or uploading never waits on AI: hooks only add the entry or image to a queue (after a short wait, so a burst of saves becomes one job). Since 0.51.0 an entry is queued only when its title or text changed since its analysis: a save that changes only links, formatting, categories or other fields that aren't its text doesn't re-analyze it, and neither do new settings (another provider or model, entities or descriptions switched on). A save's job whose title and text are back to what was analyzed by the time it runs is skipped without a model call. A scheduled job works through the queue every two minutes (or with each cron tick, if the site's cron runs less often), a few items at a time (**Items per scheduled run**; raise it on a site with a slower cron), and stops for the day at **Max model calls per day** (default 200; an entry costs up to three calls, an image one). Each run also stays under 40 outbound requests (model calls plus Wikidata lookups), so it fits the Workers Free plan's subrequest limit; entries and images take turns, so a backlog of one doesn't hold up the other. Failed items are retried after 5 and 20 minutes, then marked as errors; a retry reuses the model output it already paid for. Deleting an entry removes its analysis. **Run bulk** on the AI page queues every published entry whose title, text or settings changed since its analysis (with **Re-analyze unchanged entries**, every published entry), or every image without alt text; it's how new settings reach entries analyzed before. The AI page also has a connection test, the queue status, suggestions to review, the analyzed entities (with **Export CSV**: one row per entity with its Wikidata, Wikipedia and website links, plus each entry's AI description), and a 30-day usage log with token counts.

**Analyses made before 0.51.0** don't record the title and text alone (`textHash` in `aiEntries`), so until they do, a save re-analyzes them as before whenever the settings changed since, even when only a link changed. The scheduled run records it from each entry's current title and text, once through every analysis, a page of up to 10 per run with what its subrequest budget has left (each entry read counts 1) and no model calls; `textHashes` in `ai/status` shows how far it got (`done` once it's through). It leaves an analysis alone when the entry's title and text may not be what was analyzed: a queued analysis (that one records it), a pending draft, a save in the last two minutes (its analysis may not be queued yet), or a title other than the analyzed one; and when the entry isn't published or is gone. Those keep the old behavior until their next analysis. A queued analysis that's skipped because nothing changed (the same title, text and settings) records it too. `POST /_emdash/api/plugins/coywolf-pack/ai/text-hashes` does the same on request, with the same rules: pages of analyses (`{ limit, cursor }`, up to 50) or `{ keys: ["posts:<id>", …] }` (up to 50), and `dryRun: true` to list what it would do without writing. It answers `{ dryRun, filled, skipped, counts: { checked, filled, alreadySet, skipped }, cursor, hasMore }`: `filled` lists the keys given a text hash (in a dry run, the ones that would be), `skipped` lists `{ key, reason }` for the others (`queued`, `draft`, `recently saved`, `title changed`, `unpublished`, `missing`, `no text`, `changed meanwhile`, `error` with its message; for `keys` also `not analyzed`, `analysis failed` and `bad key`), and analyses that already had one are only counted. Pass `cursor` back while `hasMore` is true. It answers 409 while the scheduled AI run is working; try again a minute later. Only `textHash` is added: nothing else in the analysis changes, not its date, and nothing a page shows. An entry whose text changed while no analysis could be queued for it (AI Enrichment or its entities and descriptions off, its collection not covered, the queue cleared or a bulk run stopped) gets its current text's hash without an analysis of that text; **Run bulk** re-analyzes such entries, since their hash differs.

## Setup

Pick a provider on **Plugins → AI Enrichment → Settings**:

- **Cloudflare Workers AI** (the default when the binding exists). Add the binding to `wrangler.jsonc`:

  ```jsonc
  "ai": { "binding": "AI" }
  ```

  The default model is `@cf/meta/llama-4-scout-17b-16e-instruct` for both text and images. A different binding name goes in `coywolfPlugin({ ai: { binding: "MY_AI" } })`.
- **Anthropic, OpenAI, or Google Gemini** with your own API key (stored encrypted, so the site needs `EMDASH_ENCRYPTION_KEY`). Defaults (checked October 2026): `claude-sonnet-5-5`, `gpt-6-luna`, `gemini-3.8-flash`. To use another model, such as a cheaper one or a newer one after a default is retired, enter its id in **Text model** and **Image model** on the Settings tab; leave them blank to follow the defaults.

Images are sent to the model at up to 3.5 MB. With a Cloudflare Images binding (`"images": { "binding": "IMAGES" }`, the same one EmDash uses for resizing) larger images are downscaled to 1568 pixels first; without one they're skipped. SVGs are skipped.

Set `ai: false` in `coywolfPlugin()` to leave the module out entirely. The module declares the `network:request` capability (for `api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`, `www.wikidata.org`, `query.wikidata.org`, and `glossary.io`), plus content read/write, publish and revision read (the SEO panel for descriptions; entries' text for glossary.io links, which reads a pending draft to tell its own unpublished edit from someone else's), schema read, and media read, bytes, and metadata write.

## Notes

- Only published entries are analyzed, and a save re-analyzes an entry only when its title or text changed. After you change the provider or model, or switch entities or descriptions on, existing entries keep their analysis until then: **Run bulk** applies the new settings to them (it queues the entries analyzed with other settings), and with **Re-analyze unchanged entries** it re-analyzes every entry.
- The pack only reads from glossary.io: its public index, and for removing links to deleted terms, a term's public JSON. It never writes to glossary.io or asks it to create anything.
- The daily limit is counted in UTC days. Each call's token usage is in the usage log; costs depend on your provider.
- Wikidata lookups are cached per Worker isolate and made one at a time, with `maxlag=5`. If Wikidata doesn't answer, the item is retried rather than saved unverified; if it asks to slow down (HTTP 429 or maxlag), every entity job waits for its `Retry-After` without counting as a failed attempt (after 10 waits in a row, the next counts as one). When an item lists several official websites, the preferred-rank one is kept, then https over http, then the first alphabetically.
